インナーソースとは、オープンソースで培われた開発手法やプラクティスを、社内のソフトウェア開発に取り入れるアプローチです。
[会社名]ではこの取り組みを「[インナーソースの社内呼称（例：インナーソース、ソースコード社内公開活動）]」と呼びます。

重要なのは、インナーソースが単なるコード共有の仕組みではなく、**オープンソースを使いこなし、外部貢献にまでつながる文化とスキルを社内で育成するための基盤**であるという点です。社外公開が難しいコードでも、社内での共有とコラボレーションを通じてオープンソース的な恩恵を享受できます。

## なぜインナーソースが必要なのか

社内で素晴らしいソフトウェアが開発されたとしても、それを継続的に改善し、将来的にオープンソースとして公開するためには、**組織全体がオープンソースの開発手法や文化を理解し、実践できる体制**が不可欠です。

オープンソースの文化は単なる技術スキルではなく、組織の働き方や意思決定プロセスにも関わる「文化的ケイパビリティ」です。
単に「コードを公開したからオープンソースが成功する」わけではなく、**透明性・コラボレーション・継続的改善**といった価値観が組織に根付いていなければ、オープンソースの真のベネフィットは得られないほか、オープンソース公開が組織にとってリスクとなる場合もあります。

インナーソースとは、**主にチーム間のコラボレーションとコード共有を促進するために、オープンソースの原則とプラクティスを組織内で適用することを指します。**
この文脈においては、インナーソースはこうした組織的能力を育成する「安全な社内実験場」としての役割を果たします。
これにより以下の効果が期待できます：

1. **オープンソースへの道筋**

   インナーソースは組織のオープンソース活用の成熟に向けた自然な成長パスを提供します。
   コードレビュー、Issue管理、CI/CD、ドキュメンテーション、コミュニティ運営といったオープンソースで必要なスキルを、安全な内部環境で習得できます。
   この過程で従業員は透明性のある問題解決、建設的フィードバック、継続的学習といったオープンソース的思考を身につけます。
   最終的に、この経験が外部オープンソースプロジェクトへの貢献につながり、組織の技術的評価と人材獲得に寄与します。

2. **開発効率の向上**

   従来の階層的管理では、要求が各層を通過する際にバッファ時間が蓄積され、最終的にエンジニアが圧迫されます。
   インナーソースはこの構造を逆転させ、問題に最も近い人々が直接解決にあたれるようにします。
   また、組織内でのツール、ライブラリ、知識の共有により、サイロ化では実現できない相乗効果が生まれます。
   コードや知識資産は囲い込むより共有することで価値が増大化するリソースであることを、組織全体が理解するようになります。

3. **イノベーションの加速**

   インナーソースは継続的な価値創造のエコシステムを構築します。
   各チームが消費者と貢献者の両方の役割を担い、他チームのコンポーネントを活用しながら改良や新機能を還元することで、組織全体の技術レベルが向上します。
   知識循環、技術の相互発展、人材成長が相互促進する環境により、個々のプロジェクトの成功を超えた長期的競争優位性を確立できます。

4. **組織文化の改善**

   インナーソースは有機的な透明性を創出し、部門間のサイロを解消します。
   情報が自然に流通するオープンな組織文化により、支援的な職場環境が育まれ、エンジニアの満足度向上と人材定着率改善につながります。

## 社内にオープンソースの文化を根付かせるために

社内でオープンソースの文化を根付かせるためには、以下のインナーソースの4つのプリンシプルを理解し、実践することが重要です。
一方で「インナーソースでないもの」とは何かを明確にすることも必要です。
このセクションでは、インナーソースの4つのプリンシプルと、それに該当しないケースについて説明します。

### インナーソースの4つのプリンシプル

オープンソースの以下の4つの文化を社内に取り入れることが、インナーソースの成功、ひいてはオープンソースの成功に不可欠です。

1. **Openness（オープンネス）**
   ソースコードは組織内でオープンにされ、誰でも自由にアクセスできます。
   これにより、開発者は他チームのコードを参照し学ぶことができ、知識共有が活発になり、全体のスキル向上につながります。

2. **Transparency（透明性）**
   コードだけでなく、議論のプロセスも公開されます。つまり、どのように意思決定が行われたかが透明になります。
   これにより、他チームの開発者が容易に参加でき、プロジェクトが組織全体の共有資産として認識されます。

3. **Prioritized Mentorship（優先的なメンターシップ）**
    新しい開発者が参加しやすいように優先的なサポートが提供されます。
    ゲストチームの貢献をフォローし、参入障壁を下げることで、新しい貢献がプロジェクトに継続的に生まれます。

4. **Voluntary Code Contribution（自発的なコード貢献）**
    プロジェクトへの貢献は強制されません。
    プロジェクトからのサポートも自発的です。各チームはお互いを尊重し協力し合い、開発を前進させます。

### インナーソースでないもの

オープンソースの文化を社内に根付かせるためには、以下のような誤解を避けることも重要です。
こうした文化を組織の中で育てると、直接的にオープンソース活用の成功につながります。

1. **個人目的の活動**
   インナーソースは個人的な目的のための活動ではありません。
   つまり、インナーソースとは特定個人の関心に基づいてコードを書く活動ではありません。
   組織全体のニーズに応えることが求められます。
   共有やコラボレーションは、組織全体の価値を高めることを目的として行われることが望ましいです。

2. **成果物の個人所有**
    成果物は個人の所有物ではありません。
    つまり、インナーソースとは個人が作成したコードを単に他者に公開する活動ではありません。
    コードは組織全体の資産であり、誰もがアクセスできる形で管理されることが望ましいです。

3. **全員がコードを所有する**
    成果物は全員の所有物でもありません。「全員が所有する」という考え方は、責任の所在が曖昧になるリスクがあります。
    オープンソースのように、適切に「メンテナー」となるチームが責任を持ち、コードの品質と方向性を維持します。
    これを「Weak Ownership（弱い所有権）」と呼びます。

4. **隣のチームへの押し付け**
    インナーソースとは「隣のチームにコードを押し付ける」活動ではありません。
    各チームは自分たちのニーズに基づいてコードを使用し、必要に応じて貢献します。
    他チームに対する強制や義務はありません。

5. **すべてのコードを公開する**
    インナーソースはすべてのコードを公開する活動ではありません。
    つまり、インナーソースとは「すべてのコードを社内で公開する」活動ではありません。
    共有すべきコードとそうでないコードを区別し、ビジネス要件に応じて適切に管理します。

> **注意：組織をまたいだコード共有とライセンス**
> インナーソースの文脈であっても、子会社・関連会社・海外拠点・パートナー企業など、法人格の異なる組織間でOSSを含むコードを共有する場合は、ライセンス上「配布」に該当する可能性があります。社内利用に見えても法的には配布と解釈されるケースがあるため、組織境界を越える共有の際は必要に応じて税務や法務と相談し、適切なライセンスポリシーを策定することが重要です。

6. **誰もが自由に改変する**
    インナーソースは誰もが自由に改変する活動ではありません。
    つまり、インナーソースとは「誰もが組織内個人開発者になって好きに開発して自由に改変しよう」というようなものではありません。
    各チームは自分たちのニーズに基づいてコードを使用し、必要に応じて改変します。
    他チームに対する強制や義務はありません。

事例や成功例については、[InnerSource Commons Foundation](https://innersourcecommons.org/ja)を参照するほか、より具体的なプラクティスについては[インナーソース・パターンズ](https://patterns.innersourcecommons.org/)を参考にしましょう。
