# OSPO担当者向け・テンプレートの使い方

## 前提（ポリシーとの構造）

ポリシー（全社規程）は「何を守るか／誰が対象か／何を目的とするか」を定義し、具体的な手続は運用ガイドへ委任しています。
本テンプレート（この運用ドキュメント群）は、運用ガイドの実装物として整合させるようにカスタマイズします。

## はじめ方のスタンス

現時点で分からなくてもOKです。分からない点を明確にし、社内で誰に協力してもらうべきか、何を準備すべきかを明らかにしましょう。
完全版を目指して止まるより、まずは最小構成で公開し、運用しながら改善する方針を推奨します（段階的リリース）。

## OSPOがまず決めるべき「目的」

OSPOのカスタマイズは、目的によって最適解が変わります。まず何を最優先にするかを決めると、以降の判断がブレません。

例：コンプライアンス重視／セキュリティ重視／公開・貢献促進

### 4つの柱で抜けを防ぐ

カスタマイズ時の論点は、以下の4つに整理できます。迷ったらこの4分類に戻って、抜けと偏りを点検します。

- Mission：OSS活動の目的とビジョン
- Incentive：ステークホルダーの動機とベネフィット
- Compliance：法的・技術的ルールとガバナンス
- Engagement：コミュニティとの関わり方（利用・貢献・公開の段階設計）

## 優先度をつけたカスタマイズ例

### A. 運用開始に必要な項目（最初に整備する）

- ガイドの入り口となるドキュメントを整備する（[[会社名] オープンソースガイド](./about/opensource-guide.md)）
- OSSの基礎・組織ガイドを整備する（[オープンソースについて](./about/about-opensource.md) / [オープンソースの利点](./about/benefits.md)）
- [OSSを使う](./using/using-oss.md)（OSS活用の流れ・評価・ライセンス確認・導入まで網羅）
- [OSSの探し方](./using/finding-oss.md) / [社内導入済みOSSリスト](./using/oss-inventory.md)
- [OSSの評価方法](./using/evaluation.md)
- ライセンスを理解する（[オープンソースライセンスコンプライアンス](./compliance/license-compliance.md) / [ライセンスとは](./compliance/what-is-a-license.md) / [ライセンスの種類](./compliance/license-types.md)）
- [サプライヤーからのOSS入手手順](./using/supplier-procurement.md)※委託・共同開発がある組織は特に優先
- 　困ったら調べる・相談する（[OSS利用FAQ](./using/usage-faq.md) / [用語集](./about/glossary.md) / [OSPOとは](./about/ospo.md)）
- インシデント／脆弱性の報告・初動
  - ポリシーで報告・対応の枠組みが求められるため、最優先候補
- 出荷・提供前に確認する（製品・サービスとして配布/提供する組織は早期に必須）

### B. 余裕がある、または、将来段階的に目指す（運用が回り始めてから）

- 注意が必要なケース（[ソースコード提供義務のあるライセンス](./compliance/source-disclosure-licenses.md) / [商用ライセンスが選択できるOSS](./compliance/oss-with-commercial-license-options.md)）
  - → 問題が顕在化してから対応することも可能だが、SaaS提供や配布が多い組織では早期の整備を推奨（例：製品同梱・顧客提供・アプリ配布が多い場合）
- [ライセンスFAQ](./compliance/license-faq.md) / NOTICEファイル
  - → 運用が回り始めてから詳細化
- [インナーソースとは](./about/innersource.md)
  - → 社内OSS活動を促進するフェーズになってから検討
- OSSを公開する手順
  - → 自社OSSを公開しないなら後回し／公開するなら早期に必要
- 外部OSSへのコントリビューション手順
  - → 業務として貢献するフェーズになってから整備（包括許諾などで負荷を下げる）
- 私的OSS活動ガイド
  - → 社員の活動が活発化してから詳細化（守秘・名義・資源の境界を中心に）

## ステークホルダーへのメッセージの設計

テンプレートの導入・定着には、誰が「Yes」と言う必要があるか、どんな懸念（例：ライセンス、セキュリティ）を持つかを先に整理し、相手に響くメッセージを準備します。
展開後はフィードバックを集め、FAQやガイドへ還流して改善サイクルを回します。
